# Project artifact layout and maintenance

Use when registering a project, reviewing a task-named project root, or designing/accepting relocation. This concerns a product project's artifacts and managed worktrees, not moving the Controller's own source checkout; use primary-worktree-migration.md for that separate operation. Verify live CLI/docs before selecting commands: a tested helper or proposed interface is not a shipped end-to-end migration capability.

## Establish the hierarchy

1. Read the exact project's status and original registration evidence. Compare projectId, repo/commonDir, artifactsDir, worktreeRoot and actual task IDs; distinguish the repository, its project record and each feature task.
2. Choose a stable project-level container, such as `<artifacts>/<project>/taskflow/`. Keep state, receipts, logs and evidence at project scope; place individual managed worktrees under `worktrees/<task-id>/`. Do not infer that a directory is correctly scoped merely because later task IDs are siblings in state.
3. Derive every dispatch path from one verified root instead of retyping long absolute paths. Use project-ID resolution or project-relative input flags only after checking that the current CLI supports and validates them. Preserve exact identifiers; never fuzzy-repair a missing path.
4. When registration binds an unsuitable root, propose explicit history-preserving relocation. An immutable binding is a guard against silent edits, not a reason to keep misleading names forever or discard project history.

## Prepare a relocation candidate safely

1. Recheck the accepted candidate's source hashes before executing; source drift requires renewed verification rather than silently migrating with a different implementation. Save an external before snapshot covering raw state, revision, authorization/evidence identity, pending questions, complete branch refs and actual Git worktree inventory. Hash existing non-worktree artifact files as a preservation manifest; keep that manifest and maintenance input outside the moving tree so both remain available during and after the move.
2. Pause affected product tasks through the Controller. Read back paused state, confirmed terminal native runs and question expiration; then gracefully stop the runner and verify lock release. A preserved question is historical context, not a still-valid requestId after a reconnect.
3. Check ownership, exact source revision, target nonexistence, path overlap, filesystem compatibility and queued commands before moving anything. Preserve dirty, locked, unowned or uncertain scenes. Do not bypass live authorization or an unfinished acceptance/integration by renaming directories.
4. Exercise the candidate on isolated registered-local Git fixtures with synthetic permission records. Use real Git worktrees and assert exact HEAD/tree/branch/commonDir and content preservation. Test the whole CLI pause→question expiration→stop→preview→move→restart→reconcile→new question path, not just migration helpers. Assert that preview makes no writes and that misspelled preview flags are rejected before dispatch, because an ignored flag can turn an intended preview into a real move. Cover repeat relocation, legacy plus scoped integration sites, and failure retaining inspectable evidence. Focused helper tests do not replace CLI coverage, full regression or user operational acceptance.
5. Require the mechanism to update current project registration, current worktree paths and ownership metadata together while preserving original authorization, acceptance, events, native session/run observations and raw evidence. Keep a before-state snapshot and an explicit old-to-new mapping; never globally replace old paths throughout history.
6. Require durable progress evidence and exclusive ownership during the move. If interruption leaves a partial scene, fail closed and report the journal and preserved locations; do not automatically steal locks, force-move worktrees or repeatedly replay the operation. Cached success must not bypass verification of current registration and completed migration state.

## Acceptance and resumption

1. Give the user concrete candidate commands, expected observations and the exact scope of any production move. Record their actual decision bound to the candidate; approval to proceed does not prove they personally ran the preview command. Do not present isolated tests as proof that the real project already migrated.
2. After actual relocation, independently read back project identity, authorization binding, registry claim, task IDs/facts, filesystem locations, completed journal, released migration lock and `git worktree list --porcelain`. Compare complete branch refs and artifact bytes against the before manifest, and compare the saved pre-relocation state byte-for-byte. Whitelist only intended current-state/location deltas; historical runs, decisions and immutable files must not be globally rewritten.
3. Start/reuse the identified runner only on the verified source identity, including its tested fingerprint when authorized source edits remain uncommitted. Run resume and verify its successful receipt plus recovery.checked against the original thread/turn. An interrupted historical turn may make the accompanying wait report run-failed; distinguish that from failed reconciliation and do not replay it. Then explicitly continue plan, verify persisted turn.started and the actual native effective cwd at the new worktree, and obtain a fresh live question identity on the original thread. Never infer real native recovery from a synthetic peer, reuse expired answer payloads or invent product decisions.
4. Keep workflow edits, workflow commits, product commits and any push/release permission separate. Record what is implemented, what is tested, what is actually migrated and what still awaits acceptance. Never report all four as one 'done'.
