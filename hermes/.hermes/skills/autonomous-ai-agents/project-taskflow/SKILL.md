# Project Taskflow

Use the Controller for all Kenan project development, including small fixes. Hermes operates it and independently verifies deliveries; the configured backend implements. Codex is the default; Pi 1.3.0 is optional per new registration. A user may explicitly ask Hermes to maintain the workflow itself directly; that bounded exception never becomes a product-development fallback.

## When to Use

- Start or continue independent functional analysis, project tasks, direct fixes, planning, acceptance, integration or recovery. When explaining the workflow, name all three peer channels: read-only analysis, formal-plan development, and direct development. The latter two are the development lanes; analysis is neither omitted nor treated as a mandatory precursor.
- Keep workflow-design discussion read-only; do not create work or edit Skills until authorized. An explicit request for agent-led functional analysis uses the independent analysis channel, not development.
- No Hermes Kanban calls, heartbeat, board comments or mirrored task state in this workflow. Controller tasks are not Kanban cards.
- Do not switch to standalone Brief/relay when blocked, regardless of task size. Explain and resolve the blocker on the original task. Explicit one-off use of another coding tool requires the user's actual request, not an operator workaround.

## Prerequisites and Entry

The fixed entry points to this primary checkout's `scripts/taskflow.mjs`; confirm live Git/runtime identity rather than inferring it from cwd. The former self-hosted `_integration` has been migrated and removed; historical dev/task references do not identify current runtime sources, and their branches or worktrees may already have been separately cleaned. Query live Git inventory rather than assuming an old site still exists.
- Use `terminal(command="project-taskflow status --project <exact-artifacts-dir> --json")`. Installed entry: `~/.local/bin/project-taskflow`, backed by `scripts/taskflow.mjs`. It resolves the actual controller `main` checkout. If not installed, locate that checkout through `git worktree list` and invoke its absolute `scripts/taskflow.mjs` path. Never fall back to `node src/cli.mjs` in an uncertain cwd.
- The registered artifacts directory is project-scoped, not task-scoped. Choose a stable project-level root at registration; keep feature tasks as siblings beneath it, never use one feature's task name as the project container. Verify this separation in both state and disk layout: sibling task records do not make a task-named project root reasonable. Treat legacy layout as a defect to assess, not a tool requirement to defend. Existing absolute authorization, registry, evidence and worktree bindings prohibit a silent rename, not an explicitly authorized, history-preserving relocation capability. Use [project artifact layout](references/project-artifact-layout.md) when reviewing or changing that layout; never re-register the repository, rewrite old evidence or hand-edit live state to evade its binding.
- Read `docs/workflow.md` and `docs/operations.md` from `status.runtime.sourceRoot`, plus the target project's AGENTS.md. `docs/handoff.md` and old acceptance reports are history, not the current operating contract.
- Inspect actual Node/Git/backend versions. Node >=22; no Controller runtime dependencies. Verify Codex authentication only when using Codex. Do not infer version/effort from old evidence.
- Inspect `permissionStatus`, exact registration path/commonDir/branch and genuine authorization evidence. A remote never grants network, push, PR, tag, release or deployment permission.
- Establish branch topology before proposing registration changes: distinguish the primary checkout branch, the branch actually edited in a worktree, and any post-acceptance integration target. A request to work directly on an existing feature branch in a worktree means preserving that branch identity, not automatically creating a task branch and merging back. Check `git worktree list --porcelain` and `git show-ref --verify refs/heads/<exact-branch>` before selecting a location; preserve another checkout's ownership rather than forcing branch reuse. Worktrees do not inherently require new branches, and a registered integration target does not mean development happens on that branch.
- Separate the requested Git topology from Controller capabilities. Inspect the live docs/source before asserting support; when they differ, explain the precise mismatch and obtain authorization for workflow changes instead of silently changing the topology, cloning to evade registration, editing state/registry, or switching to standalone delegation. The managed task-branch procedure below is not evidence that direct development on an existing branch has been implemented. Controller `choice:direct` skips formal planning; it does not by itself select a branch topology.
- Default topology: user-selected stable product-line target (main or a long-lived feature branch) → Controller-created disposable task branch/worktree → gated integration back to that target → conservative cleanup. The selected integration target and unchanged local scope persist; do not re-ask per task. At start briefly report baseline/target/publication boundary, as information rather than a new approval. Distinguish status/task show branchContext.primaryBranch, taskBranch and integrationBranch/integrationCommit. Updating primary main never changes registration; feature-line completion never grants a main merge.
- Record local Git scope separately from push/tag/release. `project permissions` reads the current target-specific publication receipts; `project permission` saves a genuine grant/revoke with scope push/tag/release, exact target, source/statement and fresh commandId. Push target is {remote,branch}, tag target {tag}, release target {repository,tag}; the command performs no publication or local-target change. Preserve one-time/version constraints in the statement and recheck current remote identity before executing. Existing explicit named-branch push permission must not be forgotten or expanded to main/tag/release. Never backfill permission from inference. Preserve user-owned feature branches during cleanup.
- Explicitly requested runtime-layout migrations follow [primary-worktree migration](references/primary-worktree-migration.md): move Git checkout, entry and all affected idle runners as one verified operation, then retire the old site. Never assume enabling primary-worktree support already migrated an existing project.

## Project Location and Artifact Relocation

Durable records live directly under `development-artifacts/<project>/`; the Controller resolves them through the registered `artifactsDir` and `projectId`, never through a repository `.dev` link, so no project needs a `.dev` symlink and none is created by default. The historical `.dev` link convention is retired; existing links are legacy. A repository's `.dev` link, its external document target, and references in AGENTS.md remain separate maintenance scopes. When Kenan asks to unlink, verify the exact symlink target, remove only the link and preserve target contents; report remaining broken references without silently editing or deleting them. When reference cleanup is also authorized, use the normal tracked-change workflow and remove retired-document authority rather than relocating stale manuals into AGENTS.md.

Use `project-taskflow project resolve --project <projectId> --json` to resolve an existing unique repository claim; verify the returned projectId and artifactsDir before dispatch. Existing exact paths take precedence over ID lookup, so use an exact absolute registered directory if a same-named local directory makes the reference ambiguous. Dispatch with `--project <projectId> --project-input <name.json>` to derive operator-inputs from that verified project root, rather than retyping feature-named absolute paths. `--project-input` is mutually exclusive with `--input`, rejects absolute/traversal paths and symlink escapes, and never creates input files. `project init` still takes a directory path, never an existing project-ID alias.

For an explicitly approved layout repair, read `docs/project-layout.md` and [project artifact layout](references/project-artifact-layout.md). `project relocate --project <id-or-dir> --input <outside-tree.json> --dry-run --json` is read-only preflight; removing --dry-run executes the offline operation only after candidate operational acceptance. Input must stay outside the tree, carrying exact fromArtifactsDir/fromRevision, target artifactsDir and genuine new authorization with unchanged Git policy and only artifactsDir/worktreeRoot bindings moved. The runner must be stopped; acquire the exclusive migration lock rather than dispatching to an old runner. Reject queued commands, live/uncertain questions/runs/session starts, integration/cleanup, unknown/dirty/locked sites, existing plans/deliveries or execution authorization. Current support is registered-local, same filesystem, default project-local worktrees, pristine tasks or paused pre-plan Codex planning; unfinished Pi sessions are explicitly unsupported.

Use real git worktree move and verify the new exact locations. Preserve historical native thread/run observations, questions, acceptances and raw evidence; save before-state bytes and old-to-new mappings. Current integration-site ownership gets a new receipt, not rewritten historical evidence. Incomplete migration retains its lock, journal and staging sites; report them, never auto-steal locks, globally replace paths or blindly replay. Success requires a completed journal, coherent current registry/authorization, exact readback and unchanged branch refs. Then start the identified runner, reconcile the original session and explicitly continue planning; expired answers are never reused. Separate implemented/tested/accepted/actually-migrated, and do not commit merely to make source identity clean.

## Switching the Integration Target

Use `project-taskflow project switch-branch --project <exact-dir> --input <switch.json> --json` only after the user explicitly chooses the new integration target. This is a runner mutation without reasoning or `--wait`, not registration replacement or `project authorize`. Input carries commandId/projectId, exact fromBranch/fromCommit, integrationBranch/targetCommit, and genuine new localGitAuthorization with the same scope/binding except integrationBranch. Preserve existing primary-worktree permission; switch-branch enforces that it cannot be added or removed, and both legacy and scoped managed integration sites need ownership receipts. Change that permission separately via explicit project authorize. Both commits must be full current local branch tips. Re-read receipt, config target, permissionStatus and `project.integration-branch-switched`; retry unknown transport with the same identity.

Require an idle registered-local project: no live/uncertain runs, pending questions, unknown Codex/Pi session starts, task authorization, integration/queue or pending cleanup. Unfinished tasks may only be pristine pending tasks with no plan/run/delivery/worktree; finish or legitimately close started tasks first. Do not invalidate old choices or acceptance silently. The command appends authorization history and switch evidence; completed/closed task facts and old evidence remain intact. Never hand-edit state/registry, clone around a claim, or rewrite old history to rebind a project.

A switch changes subsequent task baselines and the exact post-acceptance integration target; it does not checkout any worktree, move refs, merge, push or grant task execution. Existing owned `_integration` sites stay on their old targets; when needed a new target uses `_integration-<first 16 SHA256 hex of branch name>` with its own ownership receipt. Round trips reuse the owned site. Dirty, locked, unowned or unrelated sites are preserved and rejected; primary integration still needs primaryWorktreeIntegration:true. Keep push permission scoped separately to the named branch, and do not treat a feature target as permission to merge into main or release.

### Preparing a feature-line merge into a new target

1. Verify the exact source and destination with `git show-ref --verify refs/heads/<branch>` and inspect `git worktree list --porcelain`. If a supplied branch name does not exist, obtain confirmation of the actual branch before changing registration; do not silently repair its spelling.
2. Preflight divergence with `git rev-list --left-right --count <destination>...<source>` and conflicts with `git merge-tree --write-tree <destination> <source>`. The latter leaves the index, worktrees and branch refs unchanged, but can write Git objects; exit 1 with conflict entries means a conflicted preview, not an attempted merge that must be aborted. Use it to report likely conflict areas, not to claim semantic resolution.
3. On an idle project, switch the registered target first and read back its exact branch, baseline and integration site before creating the merge task; creating or authorizing the task first can block the target switch. A target switch alone does not merge either branch.
4. If the user selects direct, record the merge requirement with both full tips and preservation/publication boundaries, then use the current direct template. Have the backend prepare the merge candidate in the Controller task worktree; leave destination updates to gated Controller integration and preserve the user-owned source branch. Treat conflict resolution and behavioral verification as unfinished until an actual candidate is delivered and independently checked.

## Independent Analysis Channel

Use this when Kenan requests agent-led feasibility/risk/complexity analysis. Read current `docs/analysis.md`. Reuse the identified runner and project backend; do not launch a standalone agent.

Delegate the user's requirement and necessary constraints, not a prescribed analysis method or report template. Trust Codex/Pi to choose how to investigate and fulfill the requirement; provide a specific method only when the user explicitly requests it. Retain workflow authorization, read-only scope and exact session/question routing as constraints, not an analysis recipe.

1. Record the user's analysis question with `task add`, `kind:"analysis"`, no dependencies. This is a discussion topic, not a settled development requirement. Use existing project registration; do not register new repositories or broaden Git authorization implicitly. Analysis does not require a clean integration site; do not treat its integration-only permissionStatus blocker as a reason to create a worktree.
2. Copy current `templates.analyze`, replace commandId, and invoke `analyze --wait` through `terminal(background=true,notify=true)`. Analysis runs in config.repo with only prompt-based read-only constraints: no worktree/branch/commit, sandbox, role-tool matrix or file-fingerprint guard. Preserve the user's existing workspace. Controller recording evidence outside the repo is expected.
3. Relay full formal questions and actual answers via current `templates.answer` and `answer --wait`. Prompts to the agent say “需要澄清时向我提问”, not “ask the user/Kenan” or an explanation of Hermes relaying.
4. `wait.kind=analysis` contains the full Markdown result and version/run/session identity. Show the conclusion and uncertainties. A round's report is not the end of discussion or development permission. For the user's follow-up, copy current `templates.feedback`, keep previousRunId and submit actual feedback with a new commandId using `feedback --wait`; preserve the exact analysis session. Do not translate feedback into formal planning.
5. Only on the user's explicit finish use `templates.close` with genuine source/reason and outcome:analysis-completed. Read back closed/resolution; no accept, integration or cleanup. Active/uncertain runs need stop/resume reconciliation first. A cancelled topic is explicitly cancelled, not a completed analysis report.
6. Later development starts only from the user's newly supplied feature requirement in a separate planning/direct task. Do not automatically cite, link, inject or bind the analysis report, create dependencies, or infer execution authorization from feasibility approval.

Codex uses Plan mode + custom analysis developer instructions (xhigh) to retain structured questions, not formal-plan choice. Pi uses configured planning thinking and native assistant text. Reports are human-facing Markdown, saved from exact native final text with host-owned identity; do not parse prose verdicts into decisions. Missing final text and failed runs are failures, not reports. Native completion can precede report persistence: wait for analysis.ready or an explicit failure; do not restart reasoning in that gap. No true-service smoke is implied by SYNTHETIC fixtures.

Apply it to both formal-plan and direct development. Reference the available `delegate-work` skill and its Codex adapter; if native skill discovery is unavailable, supply the verified skill path (current source: `~/Secret-Projects/agent_skills/skills/delegate-work/SKILL.md`) rather than assuming Codex can discover it.

Inspect the recorded child role/thread before attributing findings rather than inferring the reviewer from a parent status message.

## Development Procedure

1. **Identify and preflight.** Query the exact registered project. Read `permissionStatus`, `directEligibility.reason/next`, runner identity and task state before starting reasoning. Empty templates do not authorize an alternate workflow. New repositories require explicit registration/local Git scope.
2. **One identified runner.** Use `project-taskflow start --project <dir> --json`. It starts an exclusive runner with a unique log or confirms/reuses the exact healthy instance. Read back `runner.runtime` (source root/commit/fingerprint, Node), PID, instance and logFile. Legacy/mismatching runner or uncertain lock: inspect; explicitly stop only a confirmed idle old runner, then start. Never steal locks or restart active healthy work. A runner process executes only the Controller code it started with: after maintaining Controller source, obtain explicit authorization for any local Controller commit separately from product-repository commit/push permission; do not commit merely to obtain a clean runtime identity. With an authorized, verified source identity, stop the confirmed-idle runner and start it again before dispatching a newly added operation — a new op sent to an old runner is handled by old code and fails misleadingly.
3. **Store the full requirement.** `task add --input <json>`. For an attached requirements document, preserve its original text in durable project artifacts and include it verbatim in the task requirement, with later explicit user constraints separately identified. Preserve the document's distinction between core requirements, proposed rules and undecided scope; a request to plan is not blanket approval of its suggestions. Apply explicit user decisions over older document placeholders without silently resolving remaining product choices. Each mutation has new commandId/projectId/taskId. Read the receipt and exact target after submission. Only actual completed dependencies unlock downstream work; `closed` does not mean completed.
4. **Select the lane inside Controller.** An explicit request such as “直接修复” waives the formal-plan round for a clear small fix: copy `templates.choose`, retain requirementHash/scopeRevision/baseline, save the real user source, use a fresh UUID and `choice:"direct"`; do not ask for a second formal approval. Direct skips only planning, not task records, authorization, worktree, verification, applicable acceptance or integration. Otherwise present the full native plan and obtain real implementation approval. After that approval default to same-context; fresh-context and stay-plan remain explicit choices. The current choose API supports exact plan identity plus approved:true and real source/feedback without choice, resolved to same-context; omission alone never authorizes implementation. Revised plans require a new actual approval. On a legacy runner use explicit same-context backed by that real approval, not an unsupported new payload.
5. **Develop in the task worktree.** The backend implements, tests and commits there, not in the primary worktree. Default Codex model `gpt-6.1-sol`; Controller explicitly sets plan xhigh and execution/integration high. When the user explicitly requires all-xhigh for one task, set `reasoningEffort:"xhigh"` at `task add`: this immutable Codex-only task setting persists across new/resumed sessions, rework and integration without changing other tasks/projects. Verify `run.effective`; null is not proof. Keep requested settings, emitted RPC settings and observed native turn context distinct: a verified planning turn or synthetic lifecycle test does not establish the effort of a later execution, rework or integration turn. Recheck the actual turn when it starts rather than claiming future runs were already verified. Preserve exact thread/session identities for rework.
6. **Independent technical verification.** Load delegated-development-acceptance. Verify the exact commit/tree and complete file inventory. Re-run real checks, preferably `project-taskflow verify --project <dir> --input <checks.json> --json`: explicit cwd/commit and nonempty direct argv commands, full stdout/stderr, actual exits and before/after Git identity. No shell-pipeline summaries as evidence. Direct comparison re-run outputs (benchmarks, diagnostics) to your own verification directory, keeping the delivery's original reports as separate pristine evidence. Real behavioral fixtures need meaningful positive assertions, not print-only or tautological tests. A technical pass is not a product pass. Record the exact-candidate technical stage using the current layered template; if product judgment is needed set productRequired:true and leave that stage pending.
7. **Layered candidate acceptance.** Read current `docs/acceptance.md` and phase-specific templates. Hermes first owns independent technical verification of the exact candidate and full diff; UI paths need actual Obsidian/browser exercise, with limits disclosed. Record phase:technical with real delegation/provenance and independent evidence; automatic test evidence is separate and cannot impersonate delegated or user acceptance. Decide productRequired from whether product behavior/experience needs Kenan's judgment, not merely whether UI or operations exist. Internal behavior-preserving refactors can close within the explicit technical delegation; nonvisual search ranking may need product acceptance. If required, prepare the exact build/environment, entry, short numbered steps/expected outcomes and relevant edge cases from the delivery manifest; leave the Controller's product stage pending until his actual pass. Do not hand off first-pass bug finding. Record phase:product only with the real user decision. Controller blocks integrate/pump until the candidate's gates are met. A changed candidate requires renewed applicable checks/acceptance; preserve original evidence/history. Once gates pass, continue already-scoped integration into the registered target and disposable task cleanup without routine reconfirmation; do not infer main merge/push/tag/release scope. Honor exact separately recorded permission. A plausible diagnosis is not confirmed root cause; test-vault fixtures are not production exports; byte equality requires actual content comparison.
8. **Controller integrates and cleans.** Accepted exact versions queue for serial ff-only integration. Primary worktree may stay on main: registered-local requires genuine authorization with `primaryWorktreeIntegration:true`. Controller uses that primary worktree only for clean exact integration, never task development. If main already lives in the managed `_integration`, retain that layout. No automatic checkout/detach/stash/reset/clean. Verify task.completed, integration evidence and cleanup separately. After the acceptance gate, follow through on local integration and removal of the task worktree and task branch; do not request another routine integration/cleanup approval. Cleanup is automatic and conservative; failure preserves sites and does not undo the Controller's existing completed status, but means workflow closeout remains incomplete and must be reported proactively with the precise blocker. Verify Git worktree/branch absence before claiming cleanup. Normal generated dependencies/build artifacts are not source edits; resolve their cleanup blocker safely, never blanket-delete unknown ignored files or use force as a shortcut. Closeout recipe when auto-cleanup retained the task site: confirm tracked/index and plain-untracked are clean, list the ignored blockers with `git ls-files --others --ignored --exclude-standard --directory`, delete only regenerable artifacts (node_modules, built bundles), then non-force `git worktree remove` plus `git branch -d` from the verified integration worktree, re-verify worktree/branch absence, and append a task note recording the manual closeout so the failed auto-cleanup record stays honest. Do not repeat merges or manually push refs to bypass integration.
9. **Publish only when authorized.** Push/tag/release each need explicit user authorization. Operate in the actual integration location reported by Controller, whether primary or managed; do not switch the primary branch merely for release. For a push-only request immediately following integration, record the actual grant for that exact remote/branch and accepted commit, bounded to the requested publication rather than inventing permanent permission; read back the receipt before pushing. Recheck the push URL and local commit, then use `git -c push.followTags=false push --porcelain <remote> <full-accepted-commit>:refs/heads/<target>` without force: the exact refspec prevents branch drift, and disabling followTags prevents user Git configuration from publishing unapproved tags. Read back `git ls-remote --exit-code <remote> refs/heads/<target>` and compare the full hash. Query CI for that exact commit; for a push-only request, report an in-progress run with its URL without claiming it passed or turning the request into release work. Verify exact release assets separately when release was authorized. Publication is not external-plugin-review success.

## Recovery and Exceptional Closure

- `resume` reconciles exact native history and Git without starting reasoning. Read its receipt separately from the wait projection: after an intentional pause, receipt.ok:true and recovery.checked can coexist with wait.kind:run-failed for the historical interrupted turn. Confirm the exact recovered thread/turn, terminal status and current Git scene; do not retry successful reconciliation or label it a failed migration. Explicitly use plan to continue planning, or feedback with current authorization, previousRunId and any required recoveryWorktreeHash to continue execution. Preserve failed attempts and dirty scenes.
- After fixing a rejected command's condition, use a new UUID; reusing commandId returns the old receipt. An unknown launch/transport outcome is different: inspect and reuse the exact identity, never blindly resend reasoning.
- Outside-Controller work needs explicit exception provenance. Use `task close --input <json>` with `outcome:"external-completed"`, genuine source/reason and an already-integrated full commit. This produces `closed`, never fabricated runs/deliveries/task.completed, and never unlocks dependents. `cancelled` is also explicit. Archive only after reading back closure.
- Historical evidence defects: append `task note` with real findings/source, preserving original acceptance. Do not rewrite history or invent missing consent. New/renewed authorization goes through `project authorize`, on an idle project with exact binding and genuine source/statement. Old evidence remains preserved; no hand edits to state or registry.
- When the user prioritizes workflow repair over product work, snapshot the affected task, pause it through Controller, confirm native termination, then stop its runner before administrative relocation. Preserve questions as history but explain that interruption/reconnection expires their live answer identities. Keep product reasoning paused until the maintenance candidate passes the applicable acceptance gate; maintenance approval is not a product answer or implementation choice.

## Acceptance Policy Boundary

For the managed task-branch lane: candidate → independent technical acceptance → user product acceptance if required → exact local integration into the authorized target → disposable task cleanup. The layered Controller models the gates explicitly; a technical pass waiting for product judgment must not queue integration. Do not automatically classify all operable work as requiring user acceptance, and do not waive product judgment merely because a change has no UI. This Skill is not historical consent: never rewrite old acceptances/authorizations, fabricate a product pass or migrate/re-register a project implicitly. Verify runner.runtime before relying on new fields; an old loaded runner still has its old generic accept behavior, so withhold its final accept while a real product gate remains. Direct remains plan-free development in a disposable task worktree, not support for continuous editing on an explicitly named existing feature branch. Respect that requested branch identity and report the unsupported topology rather than silently changing it.

## Monitoring

Use the integrated single-command wait contract in `docs/notifications.md`. For `analyze/plan/choose/answer/feedback/reject/accept/integrate/resume`, call `terminal(command="project-taskflow <operation> --project <dir> --input <file> --wait --timeout-ms 600000 --json", background=true, notify=true)`. The CLI rejects missing wait/no-wait before dispatch; do not add a second shell polling loop or long-lived output-pattern monitor. `--no-wait` is intentionally silent and only for an explicit diagnostic/automation need, never an unnoticed default. Keep the terminal notification attached to the actual invoking session, not a fixed home chat. The CLI cannot enforce the Hermes tool's notify flag or prove platform delivery. A user-visible “Background task finished” card proves neither that the agent received a completion event nor that it consumed the result. Distinguish process completion, user notification delivery, agent wake-up and result handling; do not promise automatic continuation from notify:true alone. When the user reports a completion card but no follow-up, inspect the exact completed process and persisted task state, then correlate that process ID with gateway logs and session admission evidence before blaming agent inaction. Load the troubleshooting reference of the hermes-agent Skill for the wake/admission investigation. Inspect existing Hermes admission/FIFO capabilities before proposing another Taskflow queue, scheduler or polling service; a transport/admission rejection is not a missing task-state mechanism. Preserve successful task dispatches while diagnosing notification failure, and leave the exact historical cause unconfirmed unless the failed boundary is evidenced.

Normalize the saved CLI result before projecting fields: mutation commands with `--wait` return a `receipt` plus a nested `wait`, whereas standalone `project-taskflow wait` returns the wait projection at the top level. Use `projection = result.get("wait", result)` and read kind/status/cursor/runId from that projection; assuming every result has a nested wait silently hides a real timeout or question. Preserve the original JSON and any mutation receipt separately. On a background completion event, read the exact saved JSON result before responding: successful `wait.kind=question` means the backend is waiting for answers, not that planning finished. Route genuinely new questions or results, but do not repeat an already-relayed question or answer an earlier user message merely because its wait process completed. Judge operation success from its receipt and wait result rather than incidental shell-startup diagnostics. After a Controller feedback correction replaces an active planning turn, an older wait may exit nonzero with `run-failed` despite receipt.ok:true. Match its exact run ID against persisted terminal status and the replacement run before acting: report a confirmed superseded/interrupted round separately from a real current failure, preserve its evidence, and never retry the successful mutation merely to clear the old wait's exit code. A terminal background PID proves only that the CLI process launched; report backend planning/execution as started only after a successful dispatch receipt and the exact run's persisted `turn.started` identity. A client-side read failure is not a model run. In status and mutation outputs, project only the relevant identity/status/question fields before printing; keep full evidence on disk rather than dumping task.runs[].items and embedded native output into the conversation. Normalize task collections with `tasks = list(raw.values()) if isinstance(raw, dict) else raw` before iterating: saved state and CLI projections can expose different shapes. Never print a whole `run` merely to inspect progress; whitelist `id`, `finished`, `result`, `startedAt` and the needed effective-context fields, excluding nested `items` that can contain the entire native transcript. Parse and project large CLI JSON inside the terminal process (for example, `project-taskflow status ... --json | python3 -c 'import json,sys; d=json.load(sys.stdin); ...'`), or save the complete output to a file before reading it; parsing tool-returned output afterward can fail because truncation cuts otherwise valid JSON. This projection is for inspection only, not a substitute for original command exit status or verification evidence. `wait` failure/timeout does not invalidate a successful command: inspect exact state/receipt; repair transport only with the same commandId, never launch a duplicate with a new UUID. A dispatch that fails client-side before submission (CLI error reading its input, no receipt written) leaves no command record — confirm absence in state commands/events, then retry the SAME commandId; resubmission is idempotent. For ENOENT, compare the exact submitted path with the actual directory entry and registration before hypothesizing transient filesystem loss.
